\chapter{Introduction générale}

\section{Contexte du projet}

Dans un environnement informatique de plus en plus complexe et exposé aux cybermenaces,
la capacité à détecter et à répondre rapidement aux incidents de sécurité est devenue
un enjeu stratégique pour toute organisation. Les systèmes d'information modernes
génèrent des volumes massifs de journaux applicatifs (\textit{logs}) dispersés sur de
multiples services, rendant la corrélation manuelle des événements pratiquement impossible.

Le projet \textbf{SecureWatch} répond à cette problématique en proposant une plateforme
de centralisation des logs et de détection d'incidents de sécurité basée sur une
architecture microservices déployée localement via Docker. Il s'inscrit dans le cadre
des travaux pratiques de fin d'année (\textbf{PFA 2025-2026}) sur la modernisation des
systèmes d'information par l'architecture microservices et le cloud local.

\section{Problématique}

Les systèmes de sécurité traditionnels souffrent de plusieurs limitations :

\begin{itemize}[leftmargin=*]
  \item \textbf{Logs dispersés} : chaque service écrit ses journaux de manière
        indépendante, rendant la corrélation difficile.
  \item \textbf{Détection réactive} : les incidents sont souvent détectés après
        coup, lorsque les dommages sont déjà causés.
  \item \textbf{Pas de rate limiting} : les microservices exposés directement
        sont vulnérables aux attaques par force brute et aux abus d'API.
  \item \textbf{Absence de monitoring} : sans métriques temps réel, l'état de
        santé du système n'est pas observable.
\end{itemize}

\section{Objectifs}

\begin{successbox}[Objectifs du projet]
\begin{enumerate}[leftmargin=*]
  \item Centraliser tous les logs applicatifs dans un moteur de recherche unifié
        (Elasticsearch) via un pipeline automatisé.
  \item Détecter automatiquement les incidents de sécurité : brute force, accès
        interdits, rate limiting, uploads suspects.
  \item Sécuriser l'accès aux microservices via une API Gateway avec TLS, rate
        limiting et isolation réseau.
  \item Mettre en place un système de monitoring temps réel avec métriques,
        dashboards et alertes automatiques.
  \item Proposer un tableau de bord interactif accessible depuis un navigateur.
\end{enumerate}
\end{successbox}

\section{Organisation du rapport}

Ce rapport est structuré comme suit :
\begin{itemize}[leftmargin=*]
  \item \textbf{Chapitre 2} — Architecture globale et choix technologiques
  \item \textbf{Chapitre 3} — Pipeline de logs ELK Stack
  \item \textbf{Chapitre 4} — API Gateway sécurisée (Nginx HTTPS)
  \item \textbf{Chapitre 5} — Microservices Flask
  \item \textbf{Chapitre 6} — Monitoring : Prometheus, Grafana, Alertmanager

\end{itemize}

\chapter{Architecture du système}

\section{Vue d'ensemble}

SecureWatch repose sur une architecture microservices containerisée via Docker Compose,
composée de \textbf{13 conteneurs} répartis sur \textbf{3 réseaux Docker isolés}.
L'architecture suit le principe de \textit{défense en profondeur} : chaque couche ajoute
une barrière de sécurité supplémentaire.

\screenshot{architecture_diagram}{Architecture globale de SecureWatch}{architecture}

\begin{infobox}[Principe fondamental d'isolation]
Les microservices (auth-service et api-service) n'ont \textbf{aucun port exposé}
sur l'hôte. Tout trafic externe passe obligatoirement par l'API Gateway sur les
ports 8080 (HTTP → redirection) et 8443 (HTTPS).
\end{infobox}

\section{Réseaux Docker}

L'isolation réseau est assurée par trois réseaux Docker bridge distincts :

\begin{table}[H]
  \centering
  \caption{Réseaux Docker et leurs rôles}
  \begin{tabularx}{\textwidth}{@{}lX@{}}
    \toprule
    \textbf{Réseau} & \textbf{Services inclus \& rôle} \\
    \midrule
    \texttt{gateway-net}
      & gateway, auth-service, api-service, nginx-exporter, frontend.
        Routage interne : la gateway est le seul point d'entrée vers les microservices. \\
    \addlinespace
    \texttt{monitoring-net}
      & prometheus, alertmanager, grafana, node-exporter, nginx-exporter,
        auth-service, api-service, gateway.
        Permet à Prometheus de scraper les métriques de tous les services. \\
    \addlinespace
    \texttt{elk}
      & elasticsearch, logstash, kibana, filebeat, auth-service, api-service,
        gateway, frontend.
        Canal de centralisation des logs vers Elasticsearch. \\
    \bottomrule
  \end{tabularx}
\end{table}

\section{Flux de données}

\screenshot[0.90\textwidth]{flux_donnees}{Flux de données entre les composants}{flux}

Deux flux parallèles coexistent :

\begin{enumerate}[leftmargin=*]
  \item \textbf{Flux de logs (ELK)} : chaque requête est enregistrée en JSON dans
        \texttt{/logs/*.log}. Filebeat collecte ces fichiers et les envoie à Logstash
        qui enrichit et tague chaque événement avant de l'indexer dans Elasticsearch.
  \item \textbf{Flux de métriques (Prometheus)} : chaque microservice expose un endpoint
        \texttt{/metrics} au format Prometheus. Prometheus scrape ces métriques toutes les
        15 secondes. Grafana visualise et Alertmanager gère les alertes.
\end{enumerate}

\section{Choix technologiques}

\begin{table}[H]
  \centering
  \caption{Technologies utilisées et justification}
  \begin{tabularx}{\textwidth}{@{}llX@{}}

    \textbf{Technologie} & \textbf{Version} & \textbf{Justification} \\

\chapter{Pipeline de logs — ELK Stack}

\section{Vue d'ensemble du pipeline}

Le pipeline de centralisation des logs suit la chaîne :

\begin{center}
  \texttt{Services} $\rightarrow$ \texttt{/logs/*.log} $\rightarrow$
  \texttt{Filebeat} $\rightarrow$ \texttt{Logstash:5044} $\rightarrow$
  \texttt{Elasticsearch:9200} $\rightarrow$ \texttt{Kibana / Dashboard}
\end{center}

\section{Format des logs JSON}

Chaque service écrit ses logs au format JSON structuré dans un volume partagé.
Ce format est essentiel pour que Logstash puisse parser et enrichir les événements
sans règles Grok complexes.

\begin{lstlisting}[style=yaml, caption={Exemple de log brute\_force généré par auth-service}]
{
  "timestamp": "2026-05-16T02:54:36.894Z",
  "service": "auth-service",
  "level": "CRITICAL",
  "event_type": "brute_force",
  "ip": "185.220.101.5",
  "failed_attempts": 10,
  "alert_type": "BRUTE_FORCE",
  "message": "BRUTE FORCE ATTACK detected from IP 185.220.101.5"
}
\end{lstlisting}

\section{Filebeat — collecte des fichiers}

Filebeat surveille le répertoire \texttt{/logs/} et envoie chaque nouvelle ligne
vers Logstash. Sa configuration est minimale et non-intrusive.

\section{Logstash — enrichissement et tagging}

Logstash est le cœur du pipeline. Son rôle est de :
\begin{enumerate}[leftmargin=*]
  \item Parser le JSON et normaliser le champ \texttt{@timestamp}
  \item Enrichir chaque événement avec des tags de sécurité selon son type
  \item Indexer dans Elasticsearch avec le pattern \texttt{security-logs-YYYY.MM.dd}
\end{enumerate}

La logique de tagging sécurité :

\begin{table}[H]
  \centering
  \caption{Règles de tagging Logstash}
  \begin{tabularx}{\textwidth}{@{}llX@{}}
    \toprule
    \textbf{Condition} & \textbf{Tags ajoutés} & \textbf{alert\_type} \\
    \midrule
    \texttt{event\_type = brute\_force}          & brute\_force, security\_event, critical  & BRUTE\_FORCE \\
    \texttt{event\_type = auth\_failure}          & auth\_failure, security\_event           & AUTH\_FAILURE \\
    \texttt{event\_type = forbidden\_access}      & forbidden\_access, security\_event       & FORBIDDEN \\
    \texttt{event\_type = unauthorized\_access}   & unauthorized, security\_event            & UNAUTHORIZED \\
    \texttt{event\_type = suspicious\_upload}     & suspicious\_upload, security\_event      & SUSPICIOUS\_UPLOAD \\
    \texttt{status = 429}                         & rate\_limited, security\_event           & RATE\_LIMITED \\
    \texttt{level = ERROR / status = 500}         & server\_error                            & SERVER\_ERROR \\
    \texttt{service = api-gateway}                & gateway                                  & — \\
    \bottomrule
  \end{tabularx}
\end{table}

\section{Elasticsearch — stockage et indexation}

Elasticsearch indexe tous les événements dans l'index \texttt{security-logs-*}.
Il offre des capacités de recherche full-text, d'agrégation et de filtrage
nécessaires pour le dashboard SecureWatch et les alertes.

\section{Kibana — exploration des logs}

\screenshot{kibana_discover}{Kibana — index security-logs-* avec filtres de sécurité}{kibana}

Kibana permet d'explorer les logs via l'interface Discover, de créer des
visualisations et de rechercher des événements spécifiques grâce aux requêtes
KQL (\textit{Kibana Query Language}).

\chapter{API Gateway sécurisée}

\section{Rôle et position dans l'architecture}

L'API Gateway Nginx constitue l'unique point d'entrée vers les microservices.
Elle remplit quatre fonctions essentielles :

\begin{enumerate}[leftmargin=*]
  \item \textbf{Terminaison TLS} : déchiffrement HTTPS, certificat auto-signé RSA 2048
  \item \textbf{Rate limiting} : protection contre le brute force et les abus d'API
  \item \textbf{Reverse proxy} : routage des requêtes vers les microservices internes
  \item \textbf{Journalisation} : logs JSON structurés de chaque requête
\end{enumerate}

\section{Configuration HTTPS / TLS}

La gateway écoute sur deux ports :

\begin{table}[H]
  \centering
  \caption{Ports de l'API Gateway}
  \begin{tabular}{@{}lll@{}}
    \toprule
    \textbf{Port} & \textbf{Protocole} & \textbf{Comportement} \\
    \midrule
    8080 & HTTP  & Redirection 301 vers \texttt{https://<host>:8443} \\
    8443 & HTTPS & Toutes les routes API (/auth/*, /api/*) \\
    \bottomrule
  \end{tabular}
\end{table}

Les en-têtes de sécurité appliqués à toutes les réponses HTTPS :

\begin{lstlisting}[style=bash, caption={En-têtes de sécurité HTTP}]
Strict-Transport-Security: max-age=31536000; includeSubDomains
X-Frame-Options: DENY
X-Content-Type-Options: nosniff
X-XSS-Protection: 1; mode=block
X-Gateway: SecureWatch-PFA-2026
\end{lstlisting}

\section{Zones de rate limiting}

Nginx implémente le rate limiting via l'algorithme du \textit{leaky bucket} :

\begin{table}[H]
  \centering
  \caption{Zones de rate limiting configurées}
  \begin{tabular}{@{}llll@{}}
    \toprule
    \textbf{Zone} & \textbf{Limite} & \textbf{Burst} & \textbf{Cible} \\
    \midrule
    \texttt{auth\_zone}   & 5 req/min par IP  & 10  & Toutes les routes \texttt{/auth/*} \\
    \texttt{api\_zone}    & 30 req/min par IP & 50  & Toutes les routes \texttt{/api/*} \\
    \texttt{global\_zone} & 100 req/min par IP & 200 & Protection DDoS globale \\
    \bottomrule
  \end{tabular}
\end{table}

Tout dépassement retourne une réponse \textbf{HTTP 429} avec un corps JSON et
un log enregistré dans ELK avec le tag \texttt{rate\_limited}.

\begin{lstlisting}[style=yaml, caption={Réponse HTTP 429 personnalisée}]
{
  "error": "Too Many Requests",
  "message": "Rate limit exceeded. Please slow down.",
  "service": "api-gateway"
}
\end{lstlisting}

\section{Logs JSON de la gateway}

Chaque requête traversant la gateway génère un log JSON structuré :

\begin{lstlisting}[style=yaml, caption={Format de log JSON de la gateway}]
{
  "timestamp": "2026-05-16T03:15:22+00:00",
  "service": "api-gateway",
  "level": "INFO",
  "ip": "185.220.101.5",
  "method": "POST",
  "uri": "/auth/login",
  "status": 429,
  "upstream": "172.20.0.5:5001",
  "request_time": "0.002",
  "event_type": "gateway_request"
}
\end{lstlisting}

\chapter{Microservices Flask}

\section{Auth Service}

Le service d'authentification (\texttt{auth-service:5001}) gère les connexions
et émet des logs de sécurité pour chaque tentative. Il expose également des
métriques Prometheus via la bibliothèque \texttt{prometheus-flask-exporter}.

\subsection{Endpoints}

\begin{table}[H]
  \centering
  \caption{Endpoints de auth-service}
  \begin{tabular}{@{}lll@{}}
    \toprule
    \textbf{Méthode} & \textbf{Route} & \textbf{Description} \\
    \midrule
    GET  & \texttt{/health}   & Health check (retourné via gateway à \texttt{/auth/health}) \\
    POST & \texttt{/login}    & Authentification — retourne un token si succès \\
    POST & \texttt{/logout}   & Déconnexion \\
    POST & \texttt{/register} & Enregistrement d'un nouvel utilisateur \\
    GET  & \texttt{/metrics}  & Métriques Prometheus (scrappé par Prometheus) \\
    \bottomrule
  \end{tabular}
\end{table}

\subsection{Métriques Prometheus exposées}

\begin{lstlisting}[language=Python, caption={Compteurs Prometheus dans auth-service}]
from prometheus_flask_exporter import PrometheusMetrics
from prometheus_client import Counter

metrics = PrometheusMetrics(app, default_labels={'service': 'auth-service'})

auth_failures_total = Counter(
    'auth_failures_total',
    'Total authentication failures',
    ['ip']
)
brute_force_total = Counter(
    'brute_force_total',
    'Brute force attacks detected',
    ['ip']
)
\end{lstlisting}

\subsection{Détection brute force}

Auth-service détecte automatiquement les attaques brute force : si une même IP
échoue \textbf{5 fois ou plus} en peu de temps, un événement \texttt{brute\_force}
est loggé avec le niveau CRITICAL et le compteur Prometheus \texttt{brute\_force\_total}
est incrémenté.

\section{Alertmanager}

Alertmanager reçoit les alertes de Prometheus et les route selon leur sévérité.
Il implémente trois mécanismes importants :

\begin{itemize}[leftmargin=*]
  \item \textbf{Groupement} : les alertes de même nature sont regroupées
        pour éviter la multiplication des notifications.
  \item \textbf{Inhibition} : si \texttt{ServiceDown} est actif pour un job,
        les alertes infrastructure dérivées de ce même job sont supprimées.
  \item \textbf{Routage différencié} : alertes critiques → délai 10 s,
        répétition 30 min ; alertes sécurité → délai 15 s, répétition 45 min.
\end{itemize}

\section{Script de simulation}

Le fichier \texttt{scripts/generate\_attacks.py} implémente 6 scénarios d'attaque
ciblant la gateway via HTTPS (\texttt{https://localhost:8443}).

\begin{infobox}[Note HTTPS]
Depuis l'implémentation de TLS sur la gateway, le script utilise
\texttt{verify=False} pour accepter le certificat auto-signé, et les alertes
\texttt{InsecureRequestWarning} sont supprimées pour un affichage propre.
\end{infobox}

\section{Scénario 1 — Attaque Brute Force}

\textbf{Objectif} : simuler une attaque par dictionnaire sur \texttt{/auth/login}.

\begin{lstlisting}[style=bash, caption={Lancement du scénario brute force}]
python scripts/generate_attacks.py --scenario brute-force
\end{lstlisting}

\textbf{Comportement} :
\begin{itemize}[leftmargin=*]
  \item 8 à 12 tentatives avec credentials invalides depuis une IP attaquante
        (ex: 185.220.101.5, 10.0.0.5, 192.168.1.42)
  \item Chaque tentative → HTTP 401 + log \texttt{auth\_failure}
  \item Après $\geq$ 5 échecs : log \texttt{brute\_force} CRITICAL + incrémentation
        de \texttt{brute\_force\_total} dans Prometheus
\end{itemize}

\textbf{Résultats observables} :
\begin{itemize}[leftmargin=*]
  \item[\cmark] Alerte \textbf{BRUTE FORCE} dans le dashboard (section Alertes)
  \item[\cmark] Règle \texttt{BruteForceDetected} en état FIRING dans Prometheus
  \item[\cmark] Alerte active dans Alertmanager
  \item[\cmark] Logs CRITICAL visibles dans Kibana (\texttt{event\_type: brute\_force})
\end{itemize}

\section{Scénario 2 — Scan de Routes Interdites}

\textbf{Objectif} : simuler un attaquant cherchant des ressources sensibles.

\begin{lstlisting}[style=bash]
python scripts/generate_attacks.py --scenario forbidden-scan
\end{lstlisting}

Routes scannées : \texttt{/admin}, \texttt{/config}, \texttt{/secrets},
\texttt{/users}, \texttt{/debug}, \texttt{/env}, \texttt{/backup},
\texttt{/keys}, \texttt{/tokens}.

\textbf{Résultats observables} :
\begin{itemize}[leftmargin=*]
  \item[\cmark] HTTP 403 pour les routes protégées, 404 pour les routes inexistantes
  \item[\cmark] Logs \texttt{forbidden\_access} dans ELK
  \item[\cmark] Alerte \textbf{ACCÈS INTERDIT} dans le dashboard après 2 exécutions ($\geq$ 5 par IP)
\end{itemize}

\section{Scénario 6 — Test Rate Limiting}

\textbf{Objectif} : démontrer le rate limiting de la gateway en saturant les zones.

\chapter{Conclusion et perspectives}

\section{Bilan du projet}

Le projet SecureWatch atteint l'ensemble de ses objectifs initiaux :

\begin{successbox}[Réalisations]
\begin{itemize}[leftmargin=*]
  \item[\cmark] \textbf{Pipeline de logs complet} : Filebeat → Logstash (tagging sécurité) → Elasticsearch → Kibana
  \item[\cmark] \textbf{API Gateway HTTPS} : TLS auto-signé, rate limiting 3 zones, logs JSON, isolation réseau
  \item[\cmark] \textbf{Monitoring temps réel} : Prometheus (5 targets), Grafana (2 dashboards auto), Alertmanager (8 règles)
  \item[\cmark] \textbf{Dashboard interactif} : 4 sections, panels Chart.js, détection d'incidents, source hybride ES/Prometheus
  \item[\cmark] \textbf{Simulation d'attaques} : 6 scénarios couvrant brute force, forbidden scan, rate limiting, uploads suspects
  \item[\cmark] \textbf{13 services} orchestrés via Docker Compose sur 3 réseaux isolés
\end{itemize}
\end{successbox}

\section{Difficultés rencontrées}

\begin{itemize}[leftmargin=*]
  \item \textbf{Initialisation des graphiques Chart.js} : les canvas dans des sections
        masquées (\texttt{display:none}) ont des dimensions nulles. Résolu par une
        initialisation paresseuse (\textit{lazy init}) déclenchée uniquement lors de
        la navigation vers la section Monitoring.
  \item \textbf{Métriques 429 absentes de Prometheus} : Nginx bloque les requêtes
        rate-limitées avant qu'elles n'atteignent Flask. Résolu en interrogeant
        Elasticsearch directement pour les données 429.
  \item \textbf{Cache DNS Nginx} : après recréation d'un conteneur, le frontend Nginx
        conserve l'ancienne IP Prometheus. Résolu par \texttt{nginx -s reload}.
  \item \textbf{Flood de health\_check} : les 2\,745 événements de health check
        occupaient les 1\,000 premiers résultats de la requête ES, masquant les
        événements de sécurité. Résolu en excluant ces types via \texttt{must\_not}.
\end{itemize}

\section{Perspectives d'évolution}

\begin{itemize}[leftmargin=*]
  \item \textbf{Notifications Alertmanager} : configurer des receivers email/Slack/Discord
        pour les alertes critiques en production.
  \item \textbf{Certificat TLS signé par CA} : remplacer le certificat auto-signé
        par Let's Encrypt ou une CA interne.
  \item \textbf{Authentification dashboard} : ajouter une couche d'authentification
        (JWT ou session) sur SecureWatch lui-même.
  \item \textbf{Machine learning} : intégrer des modèles de détection d'anomalies
        sur les séries temporelles Prometheus (ex: LSTM pour les pics de trafic).
  \item \textbf{Déploiement cloud} : porter l'architecture sur Kubernetes avec
        Helm charts pour un déploiement en production.
  \item \textbf{Tests de charge} : intégrer Locust ou k6 pour des tests de performance
        automatisés et calibrer les zones de rate limiting.
\end{itemize}
